# Prerequisites

Install: `doctl`, `terraform`, `kubectl`, `helm`, `docker`, `jq`. Then authenticate the DigitalOcean
CLI:

```
doctl auth init
```

The bootstrap script re-checks all of these (and that `doctl account get` succeeds) before doing
anything, so a missing tool or an expired token fails immediately rather than partway through.

# Accounts and External Services Needed

Have these ready before you start:

- A DigitalOcean account, with an API token and a Spaces access key pair.
- A domain you control DNS for.
- A Google Cloud OAuth 2.0 client, with redirect URI `https://<your-domain>/api/auth/callback`.
- An FRC Events API key (register at frc-events.firstinspires.org) — and an FTC Events API key too,
  if you'll run FTC events.
- A GitHub account or organization to host container images in GitHub Container Registry (GHCR).

# Environment Configuration

Copy the example environment file and fill in your own values:

```
cp .env.example .env
```

The file groups roughly into:

- **Auth/app**: `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET`, `TOKEN_ENCRYPTION_KEY`, `SESSION_SECRET`,
  `ADMIN_EMAIL`, `CONTACT_EMAIL`
- **Third-party APIs**: `FRC_API_USERNAME`, `FRC_API_TOKEN`, `FTC_API_USERNAME`, `FTC_API_TOKEN`,
  `GITHUB_TOKEN` (for OBS plugin releases), `SLACK_CLIENT_ID`, `SLACK_CLIENT_SECRET`
- **Deployment**: `APP_DOMAIN`, `GHCR_OWNER`, `GHCR_TOKEN` (or a GitHub App via `GITHUB_APP_ID` /
  `GITHUB_APP_INSTALLATION_ID` plus a `.pem` key file), `K8S_VERSION`
- **DigitalOcean**: `DO_TOKEN`, `DO_REGION` (your DigitalOcean region, e.g. `<region>`),
  `SPACES_ACCESS_KEY`, `SPACES_SECRET_KEY`, `SPACES_BUCKET` (pick your own bucket name — bucket
  names are visible in endpoint URLs, so don't put anything sensitive in it)

See
[[Event-Streaming-Management/System-Administration/3. Configuration and Secrets Reference|Configuration and Secrets Reference]] for what each of these is for.

# Building and Pushing Images

In normal operation you won't build images by hand: pushing a version tag (see
[[Event-Streaming-Management/System-Administration/5. Upgrades, Migrations and Rollback|Upgrades, Migrations and Rollback]]) triggers CI to build and push every service automatically. For a
first-time manual build, build and push each service's image to GHCR — repeated for every directory
under `services/`:

```
docker build -t "ghcr.io/${GHCR_OWNER}/<image-path>/${SERVICE}:latest" "services/${SERVICE}/"
docker push "ghcr.io/${GHCR_OWNER}/<image-path>/${SERVICE}:latest"
```

`<image-path>` is a fixed path segment shared by every service's image — pick anything you like, as
long as it's consistent between the build/push commands above and the manifests the bootstrap script
renders.

# Running the Bootstrap Script

```
./scripts/bootstrap-do.sh
```

Run with no flags, this is idempotent — safe to re-run if a step fails partway through. It:

1. Runs the Terraform configuration to create the Kubernetes cluster, Spaces bucket, and firewall.
2. Fetches a kubeconfig for the new cluster and waits for nodes and core system components to be
   ready.
3. Installs `ingress-nginx` (with TCP passthrough configured for RTMP on port 1935), `cert-manager`
   (with its webhook timeout overridden — see the warning below), `csi-driver-nfs`, and
   `metrics-server`.
4. Creates the Kubernetes secrets the services need from your `.env` values, plus a separate GitHub
   token secret mounted only into api-server.
5. Renders the manifests — substituting your domain, ACME account email, and Spaces endpoint for
   their placeholders — and applies them in dependency order: namespace and RBAC first, then
   storage and infrastructure (Postgres, Redis, NFS), then each service, then ingress.
6. Initializes the database on first run (or applies any pending migrations if it's already
   initialized) and seeds your `ADMIN_EMAIL` as the platform's first system admin.

> [!warning] `--destroy` and `--force-destroy` Are Not Safe Re-Run Flags
> `--destroy` removes Terraform's destroy protection from **all** resources it manages — including
> the object-storage bucket holding every recording and clip, not just the cluster — and it also
> skips the script's normal auto-import of already-existing infrastructure into Terraform's state.
> With protection off and auto-import skipped, the plan it prints can propose destroying or
> replacing the cluster and the bucket. Read that printed plan line by line before answering the
> confirmation prompt. Only use `--destroy` when you actually intend to replace infrastructure.
> `--force-destroy` goes further: it tears down everything Terraform created and exits — there is no
> undo. The "safe to re-run" idempotency described above is about running the script with **neither**
> flag.

> [!warning] DOKS Control-Plane Upgrades and Admission Webhooks
> If your cluster is DigitalOcean Kubernetes (DOKS), DOKS refuses control-plane upgrades if any
> admission webhook's timeout is outside 1–29 seconds. cert-manager's default webhook timeout is 30
> seconds; the bootstrap script overrides it to 29 automatically. If you install or upgrade any
> other webhook-registering chart by hand later, check its timeout too:
> ```
> kubectl get validatingwebhookconfigurations,mutatingwebhookconfigurations \
>   -o jsonpath='{range .items[*]}{.metadata.name}{"\n"}{range .webhooks[*]}  {.name} = {.timeoutSeconds}{"\n"}{end}{end}'
> ```

# DNS and TLS

Once the script prints the load balancer's IP address, create an A record pointing your domain at
it. TLS is issued automatically by cert-manager via Let's Encrypt once DNS resolves and the ingress
sees traffic on port 80 for the ACME HTTP-01 challenge — no manual certificate steps are needed.

# Verifying the Deploy

```
export KUBECONFIG=~/.kube/config-do-<namespace>
kubectl get pods -n <namespace>
kubectl logs -n <namespace> -l app=api-server --tail=50
kubectl get svc ingress-nginx-controller -n ingress-nginx
```

`<namespace>` here and throughout this manual is the namespace your manifests deploy into.

Then browse to `https://<your-domain>` (it redirects to `/admin`) and confirm you can sign in as
your seeded admin. Test RTMP ingest against `rtmp://<your-domain>/live/<stream-key>` before
considering the install complete. Afterward, day-to-day health checking uses the same Status/Logs
view described in
[[Event-Streaming-Management/System-Administration/6. Monitoring and Troubleshooting|Monitoring and Troubleshooting]] — worth confirming it looks right immediately after install too.

# Tearing Down

Two different scripts, for two different amounts of destruction:

- `./scripts/cleanup-do.sh` — removes the application (deployments, services, autoscalers, the
  ConfigMap, ingress, and the TLS issuer) but preserves the cluster itself, persistent volumes, the
  namespace, RBAC, the Kubernetes Secret objects, and the ingress-nginx/cert-manager infrastructure.
  Use this to tear down the app without losing the cluster or your data. Keep your `.env` values
  around either way — redeploying with the bootstrap script re-applies the Secret objects from them
  regardless of whether cleanup touched them.
- `./scripts/bootstrap-do.sh --force-destroy` — tears down everything Terraform created: the
  cluster, the Spaces bucket, and the firewall. There is no undo; be certain before running this.
