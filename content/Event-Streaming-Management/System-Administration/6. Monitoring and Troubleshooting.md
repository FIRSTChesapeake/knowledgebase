# Status Page

The admin **Status** page is a live view of the whole cluster — start here first when something
seems off. It shows:

- **Live Events** — events happening today, which are live right now, and aggregate stream metrics
  (average bitrate, ingress/egress transfer rate) pulled from the same per-stream measurements
  stream-auth records for health checking.
- **Services** — one card per deployment (the twelve listed in
  [[Event-Streaming-Management/System-Administration/1. Architecture Overview#Services|Architecture Overview]]), each showing a health state (healthy / degraded / down / unknown),
  desired vs. ready pod counts, and per-pod detail: restart count, age, phase, and — when a pod is
  unhealthy — a reason like `CrashLoopBackOff`, `OOMKilled`, or `ImagePullBackOff`. Each card has a
  **Restart** button.
- **Cluster Resources** — aggregate and per-node CPU/memory usage, pod counts, and node conditions
  (Ready, and pressure flags for memory/disk/PID/network). This needs `metrics-server` installed
  (the bootstrap script installs it); without it, this section shows "Metrics unavailable."
- **Storage** — recordings (NFS) and object storage (S3-compatible) usage and clip counts, database
  size, and Redis memory usage, plus a table of every PVC with its capacity and used/available
  bytes.
- **Queue Depths** — the length of each of the eight job queues described in
  [[Event-Streaming-Management/System-Administration/1. Architecture Overview#The Pipeline|Architecture Overview]].
- **Worker Scaling** — for each background worker: current pods (ready/desired), its configured
  min–max replica range (see
  [[Event-Streaming-Management/System-Administration/4. System Settings Reference#Scaling|System Settings Reference]]), its queue depth, and a utilization bar that turns red once a
  worker is over 80% of its max range with a nonzero queue — the visual cue that it's time to raise
  the max, not just wait.

# Logs

The admin **Logs** page streams pod logs directly from the cluster (with a live-tail option), plus a
pod-events feed (starts, restarts, scheduling failures) — so you don't need `kubectl` access day to
day to see what a service is doing. This is system-admin-only; there's no client-facing equivalent
at any role, since pod logs can span every Client's activity.

# Jobs

The admin **Jobs** page shows queue depth for each pipeline stage (see
[[Event-Streaming-Management/System-Administration/1. Architecture Overview#The Pipeline|Architecture Overview]]), plus actions to pause/resume a queue, requeue or clear failed items in
bulk, and force-release a mode-deferred upload. A backlog here usually means a downstream service is
stuck, crash-looping, or scaled down too far. "YouTube uploads paused" here means either the
system-wide quota limit or the current Operation Mode — see
[[Event-Streaming-Management/System-Administration/4. System Settings Reference#YouTube|System Settings Reference]].

Unlike the Status and Logs pages, Jobs isn't backed by Kubernetes at all — the queues themselves are
Redis lists, so there's no `kubectl` equivalent for most of what this page does (see
[[#kubectl Equivalents]]).

# Health-Check Banners

The same health-warning banners operators see (see
[[Event-Streaming-Management/Operators/6. Troubleshooting|Troubleshooting]]) come from explicit checks the platform runs against each live
stream, only while its restream mode isn't "none":

- **Incompatible video codec** (error) — the incoming video codec isn't one YouTube's ingest
  accepts (H.264, AV1, HEVC, or VP9). The banner names the actual codec detected and suggests
  switching encoders or enabling re-encoding.
- **Incompatible audio codec** (error) — the incoming audio codec isn't AAC. Same remedy.
- **Keyframe interval too long** (warning) — only checked if keyframe checking is turned on (see
  [[Event-Streaming-Management/System-Administration/4. System Settings Reference#Ingest|System Settings Reference]], off by default). YouTube requires a keyframe interval of 4
  seconds or less (2s recommended); the banner reports the measured interval, or "at least Ns" if
  the platform's 15-second measurement window didn't catch two full keyframes.
- **YouTube-reported ingest issues** — for broadcasts using the Livestream Control Center path,
  YouTube's own reported ingest health issues are surfaced verbatim, prefixed "YouTube reports:".

Enabling **re-encoding** (see
[[Event-Streaming-Management/System-Administration/4. System Settings Reference#YouTube|System Settings Reference]]) disables the codec-compatibility checks entirely, since a
re-encoded stream is normalized to a compatible codec regardless of what came in.

If an operator reports a warning you can't explain from the Operators troubleshooting page, check
the Status and Logs pages for the specific service next — usually rtmp-ingest or restream-pusher,
depending on the warning.

# YouTube Channel Re-Authentication

A linked YouTube channel that fails to refresh its access token is flagged as needing
re-authentication; uploads and restreams using it will fail until an admin re-links it (see
[[Event-Streaming-Management/Client-Administration/3. YouTube and Slack Integrations#Linking a YouTube Channel|YouTube and Slack Integrations]]). This is a per-Client action — a system admin can see that a
channel is flagged, but only that Client's admin can complete the re-link.

# kubectl Equivalents

Most of the admin dashboard's cluster-facing pages map onto raw `kubectl` commands, if you'd rather
work from a terminal or the dashboard is unreachable. `<namespace>` below is the namespace your
manifests deploy into:

| Dashboard feature | `kubectl` equivalent |
|---|---|
| Status → Services | `kubectl get deployments -n <namespace>` / `kubectl get pods -n <namespace> -o wide` |
| Status → Restart | `kubectl rollout restart deployment/<service> -n <namespace>` |
| Status → Cluster Resources | `kubectl top nodes` / `kubectl get nodes -o json` |
| Status → Storage (PVCs) | `kubectl get pvc -n <namespace>` |
| Logs → per-service | `kubectl logs -n <namespace> -l app=<service> --tail=200 --timestamps` |
| Logs → live tail | `kubectl logs -f -n <namespace> <pod-name>` |
| Logs → pod events | `kubectl get events -n <namespace> --sort-by=.lastTimestamp` |
| Jobs → queue depth | No kubectl equivalent — it's Redis: `kubectl exec -n <namespace> deploy/redis -- redis-cli llen queue:clip-jobs` |

The Jobs page's other actions (pause/resume a queue, bulk requeue/clear, force-release a deferred
upload) mutate Redis and the database directly and have no raw `kubectl` equivalent at all — use the
dashboard for those.
