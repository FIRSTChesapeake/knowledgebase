# Services

The platform is a set of independently-deployed services, each doing one job:

- **api-server** — the API and auth backend the web dashboard and OBS plugin talk to.
- **rtmp-ingest** — receives incoming RTMP streams.
- **stream-auth** — authorizes incoming streams against stream keys, and measures stream health
  (codec, keyframe interval, bitrate).
- **first-poller** — polls the *FIRST* Events APIs for schedules and match results.
- **clipper** — cuts per-match clips from recordings.
- **s3-mover** — moves finished recordings/clips to object storage.
- **uploader** — uploads clips to YouTube.
- **blue-alliance** — posts FRC results/video links back to The Blue Alliance.
- **slack-notifier** — sends event notifications to Slack.
- **signage-controller** — drives event signage displays.
- **restream-pusher** — pushes the live restream toward YouTube.
- **web-frontend** — the dashboard UI.

The OBS plugin talks to api-server's device-auth endpoints; it isn't a separate deployed service.
These twelve names are also exactly the deployments the admin Status page and restart action know
about — see
[[Event-Streaming-Management/System-Administration/6. Monitoring and Troubleshooting#Status Page|Monitoring and Troubleshooting]].

# The Pipeline

Work moves between services through eight named job queues (Redis lists, not a Kubernetes concept),
each corresponding to one pipeline stage:

| Queue | Fed by | Consumed by |
|---|---|---|
| `queue:clip-jobs` | rtmp-ingest, at match end | clipper |
| `queue:s3-move-jobs` | clipper | s3-mover |
| `queue:upload-jobs` | s3-mover | uploader |
| `queue:upload-deferred` | uploader, when Operation Mode defers a clip | uploader, on release |
| `queue:tba-jobs` | uploader, after a successful FRC upload | blue-alliance |
| `queue:slack-notifications` | multiple services, on success/failure | slack-notifier |
| `queue:signage-jobs` | event/sign configuration changes | signage-controller |
| `queue:restream-jobs` | the Livestream Control Center | restream-pusher |

Roughly, the main recording/upload chain runs:

```
RTMP ingest → clip jobs → storage-move jobs → upload jobs → Blue Alliance / Slack notification jobs
```

Signage and restreaming run as their own separate queues alongside this main chain, driven by the
same event configuration. A backlog in any queue usually means its consumer is stuck, crash-looping,
or scaled down too far — see
[[Event-Streaming-Management/System-Administration/6. Monitoring and Troubleshooting#Jobs|Monitoring and Troubleshooting]] for how to check queue depth and
[[Event-Streaming-Management/System-Administration/4. System Settings Reference#Scaling|System Settings Reference]] for adjusting worker replica counts.

# Operation Modes

A system-wide **Operation Mode** setting — `record_only`, `lite_mode`, or `full_power` — is shown as
a banner in both the admin and client dashboards. It's easy to assume this gates recording itself;
it doesn't. What it actually gates, precisely:

| Mode | Recording & clipping | YouTube upload | Playlists | Blue Alliance video submission |
|---|---|---|---|---|
| `record_only` (default) | Runs normally | Deferred (queued, not sent) | — | Never |
| `lite_mode` | Runs normally | Sent | Skipped | Sent |
| `full_power` | Runs normally | Sent | Created/managed | Sent |

In every mode, ingest, recording, and clipping happen the same way — a clip file is always produced
and moved to storage regardless of Operation Mode. What changes is only whether the resulting
upload job is actually sent to YouTube's API. In `record_only`, that job sits in
`queue:upload-deferred` until either the mode changes or a system admin force-releases it — see
[[Event-Streaming-Management/System-Administration/4. System Settings Reference#General|System Settings Reference]].
