[[#Settings That Change What Operators See]]

The system admin **Settings** page is organized into tabs, one row per setting. Every setting here
is system-admin-only — there's no client-level equivalent for anything on this page. This is a
field-by-field reference; for the workflows that actually change these day-to-day, see
[[Event-Streaming-Management/System-Administration/4. System Admins and Test Mode|System Admins and Test Mode]] and
[[Event-Streaming-Management/System-Administration/3. Monitoring and Troubleshooting|Monitoring and Troubleshooting]].
If a value is refused when you save it, the reason also appears under that setting's row.

# General

| Setting | Default | Purpose |
|---|---|---|
| Operation Mode | **Record Only** (`record_only`) | See [[Event-Streaming-Management/System-Administration/1. Architecture Overview#Operation Modes|Architecture Overview]] for exactly what each of the three modes (**Record Only**, **Lite Mode**, **Full Power**) does. Rendered as a 3-button mode card, not a dropdown. |
| Sweep Interval (hours) | `6` | Hours between automatic orphan-file sweeps of clips and raw recordings. Set to `0` to disable. A **Sweep Now** button runs one immediately without waiting for the interval. |

Switching out of `record_only` doesn't retroactively push out deferred uploads by itself. While
uploads are deferred, the General tab shows a banner: "⚠️ *N* uploads are currently deferred due to
operation mode." In **Record Only** it adds "Switch to Lite Mode or Full Power, then release from
the Jobs page."; in the other modes it points you to the **Upload Deferred** queue on the Jobs page.
The release actions live there, on the `queue:upload-deferred` card: **Release Mode Deferred**,
**Release Paused**, and a per-row **Force Release** — see
[[Event-Streaming-Management/System-Administration/3. Monitoring and Troubleshooting#Jobs|Monitoring and Troubleshooting]].

# Scaling

One row per background worker, each a **min / max replica count** pair. Saving a row directly
patches that worker's Kubernetes Deployment replica count — there's no real autoscaler behind this;
raising the minimum scales up immediately, lowering the maximum only clamps down if the worker is
currently above it.

| Worker | Min default | Max default |
|---|---|---|
| Clipper | 1 | 5 |
| S3 Mover | 1 | 3 |
| Uploader | 1 | 3 |
| Blue Alliance | 1 | 2 |
| Slack Notifier | 1 | 2 |
| Signage Controller | 1 | 1 |
| Restream Pusher | 1 | 1 |

If a queue is backing up and its worker is already at its max, raise the max here before assuming
something is broken — see
[[Event-Streaming-Management/System-Administration/3. Monitoring and Troubleshooting#Jobs|Monitoring and Troubleshooting]].

# Clipping

| Setting | Default | Purpose |
|---|---|---|
| Clip Padding Before (s) / Clip Padding After (s) | 30s / 60s | Extra seconds captured before/after a match's official window when cutting a clip. |
| Clipping Tolerance (s) | 10s | How much shorter than expected a clip's actual duration can be before it's held in **Needs Review** instead of being queued for upload automatically — see [[Event-Streaming-Management/Operators/5. Clips, Uploads and Signage#Reviewing Clips|Clips, Uploads and Signage]]. A **User** or above (or a system admin) then approves it for upload or discards it; the platform no longer deletes short clips and marks the match missed on its own. |
| Auto-Discard Needs-Review Clips (days) (`needs_review_auto_discard_days`) | `0` (never) | **Not on the Settings page** — this value is set in the database only. When set to N, a clip still sitting in **Needs Review** after N days is discarded automatically — same outcome as a manual Discard — and recorded in the audit log with the setting itself as the actor, shown as a "system" actor in the admin audit log. A value that isn't a whole number, or is negative, is treated as `0` (auto-discard disabled); anything above `3650` is capped at `3650`. Each hourly pass discards at most 200 clips, oldest first, so a larger backlog clears over several passes rather than all at once. |
| Start Delay (s) | 10s | Delay before a dequeued clip job actually extracts its clip, so the raw recording segment has time to finish flushing to disk. |
| Max Clip Retries | 3 | How many times a failed clip extraction is retried before landing in Jobs as permanently failed. |
| Stale Clip Sweep | on / 15 min | A clip job stuck past this timeout is treated as failed and swept (ffmpeg itself times out at 10 minutes; 15 gives overhead). |
| Fade In / Fade Out | off / 14 frames each | Optional fade at clip start/end, in frames at the clip's native frame rate. |
| Cleanup EFS After S3 Move | on | Delete the on-disk copy once it's safely in object storage. |
| Minimum free disk space (GB) on recordings volume before blocking new streams | 5 GB | Minimum free space on the recordings volume before the platform blocks new streams rather than risk filling the disk mid-recording. |

# Branding

| Setting | Default | Purpose |
|---|---|---|
| Post-Roll Enabled | off | Whether the platform-wide post-roll asset is appended to clips. |
| Pre-Roll Enabled | off | Platform-wide kill switch for pre-roll application (per-Client assets and the per-event checkbox still apply on top of this). |
| Pre-Roll Overlay | on | An overlay behavior for how pre-roll is composited — leave on unless you have a specific reason to change it. |

Pre-roll and post-roll video files themselves are uploaded from the admin Clients page (per-Client
pre-roll) and this Settings page's asset uploader (platform-wide post-roll), not typed in as
settings — see
[[Event-Streaming-Management/Client-Administration/4. Branding#Pre-Roll and Post-Roll Video (Not Here)|Branding]].
Each file is capped at 100 MB by the application itself; the ingress proxy in front of it allows a
little more headroom (up to 110 MB) before rejecting anything larger outright with an immediate HTTP
413, so a file just over the 100 MB app limit but still under 110 MB reaches the application and gets
rejected there instead. Every other request to the platform is capped at 4 MB by the same proxy. If
you or a Client Admin see a 413 on a branding upload, re-export the video smaller rather than
retrying the same file.

# YouTube

- **Quota Throttle** (with **Daily Limit**) — the platform's YouTube Data API usage is a **single
  system-wide daily quota**, not a per-Client quota. `youtube_quota_throttle_enabled` (default on)
  turns throttling on at all; `youtube_daily_quota_limit` is the budget itself, in units/day — set
  it to match whatever daily quota Google has actually granted your API project, not a guess. When
  the budget is nearly spent, uploads across every Client can show as paused — see
  [[Event-Streaming-Management/Operators/5. Clips, Uploads and Signage#Uploads|Clips, Uploads and Signage]].
  Per-action costs are also settings, not hardcoded: a video upload costs 100 units and a
  playlist insert costs 50 units by default; the live-broadcast and live-stream costs (50 units each
  by default) are explicitly marked in the platform as provisional estimates, since YouTube doesn't
  publish an official figure for those two.
- **Upload Privacy** — default `unlisted` (options: `public`, `unlisted`, `private`) for videos the
  platform uploads.
- **Auto Token Refresh** — on by default, with a configurable **Window (min)** (default 15
  minutes before expiry) and a **Token Expiry Fallback (s)** (default 3600s) for channels that don't
  report their own token lifetime.
- **Description Footer** — text appended to every uploaded video's description; blank by default.
- **Max Upload Retries** / **Deferred Check Interval (min)** — default 3 retries; deferred (mode-blocked)
  uploads are re-checked for release every 60 minutes by default.
- **Restream switches** — three independent on/off switches. Which of the first two applies to a
  given event is decided by that event's own restream mode (**None**, **YouTube channel
  (system-managed broadcasts)**, or **Manual RTMP key**):
  - **Manual-Key Re-Streaming** (`manual_key_restream_enabled`, default **on**) — a kill switch for
    events set to **Manual RTMP key** mode, where the push goes straight to a pasted stream key
    entered as a restream key.
  - **Restream Integration Enabled** (`restream_integration_enabled`, default **off**, in the
    **Livestream Restreaming** group) — governs the platform-managed path used by events set to
    **YouTube channel (system-managed broadcasts)** mode, which creates one YouTube broadcast per
    broadcast day through YouTube's Live Streaming API. This is the standard, supported way an event
    restreams to YouTube; the setting simply ships off in a fresh install, and is expected to be
    turned on in production. While it's off, **Start Push** and **Go Live** are disabled with
    "🔒 Turned off by system administrators"; **Stop Push** and **Stop Broadcast** still work.
  - **Restream Re-encode Enabled** (`restream_reencode_enabled`, default **off**) — see
    [[#Re-encoding Restreamed Sources]] below.

  The first two are not interchangeable and don't have to be set the same way.

**Livestream Restreaming** group:

| Setting | Default | Purpose |
|---|---|---|
| Restream Integration Enabled | off | See the restream switches above. |
| Restream Poll Interval (s) | 30 | Seconds between restream-pusher reconcile passes, which drive each push toward its desired state. |
| Restream Re-encode Enabled | off | See [[#Re-encoding Restreamed Sources]]. |
| Restream Hold Timeout (s) (`restream_hold_timeout_s`) | 600 | "How long (in seconds) restream-pusher holds a YouTube push open on a generated slate after the OBS source drops, before giving up and marking the push as errored." It also bounds how long a push waits for a source that never started publishing. Operators see it as the "gives up in *m:ss*" countdown on the **Holding — standby slate on YouTube** row. |
| YouTube Live Reconcile Interval (s) | 15 | Seconds between api-server's passes reconciling the platform's YouTube Live broadcasts with YouTube. |
| Live Broadcast Quota Cost / Live Stream Quota Cost | 50 / 50 | Quota units counted per live-broadcast write call (insert, bind, transition) and per live-stream call — provisional estimates, see **Quota Throttle** above. |

## Re-encoding Restreamed Sources

**Restream Re-encode Enabled** is off by default; enable it only if your source isn't copy-safe for
YouTube's ingest (for example, its keyframe interval/GOP), since re-encoding costs CPU.

- **Off (copy mode)**: video and audio pass through unchanged. YouTube accepts H.264, AV1, HEVC and
  VP9 video, so none of those is refused; VP8 is refused. Audio must already be AAC.
- **On**: every source is re-encoded, H.264 included, within its own codec family — H.264 → H.264,
  AV1 → AV1, VP9 and VP8 → VP9 — except HEVC, which becomes H.264 because the image has no HEVC
  encoder. Audio is always re-encoded to AAC. VP8 can be pushed only with re-encode on.

Turning re-encode on also skips the whole YouTube-ingest-compatibility health check, the keyframe
check included — see
[[Event-Streaming-Management/System-Administration/3. Monitoring and Troubleshooting#Source Codec Rules|Source Codec Rules]].

# Blue Alliance

- **Blue Alliance Enabled** — default **off**. When on, the platform submits match video links to
  The Blue Alliance's Trusted API after a successful YouTube upload — but only while Operation Mode
  is `lite_mode` or `full_power`; it never runs in `record_only` regardless of this setting (see
  [[Event-Streaming-Management/System-Administration/1. Architecture Overview#Operation Modes|Architecture Overview]]).

Per-event Blue Alliance credentials are set from
[[Event-Streaming-Management/Client-Administration/6. Event Configuration Reference#Blue Alliance Credentials (FRC Only)|Event Configuration Reference]], not here.

# OBS

- **Encoder Profile** — the output settings pushed to every paired OBS plugin the next time it
  checks in. These are the actual values applied, not just a recommendation:

  | Setting | Default |
  |---|---|
  | Output Resolution | 1920x1080 |
  | Frame Rate (fps) | 30 fps |
  | Video Bitrate (kbps) | 4500 kbps (the platform's own note: YouTube recommends 3000–6000 kbps for 1080p30 live) |
  | Keyframe Interval (s) | 2s (YouTube requires ≤ 4s) |
  | Rate Control | CBR (YouTube requires CBR for live streaming) |
  | Video Encoder | `auto` (or force x264 / NVENC / QuickSync / AMF) |
  | Audio Bitrate (kbps) | 128 kbps |
  | Audio Sample Rate (Hz) | 44100 Hz |

- **Plugin Distribution** — **Plugin Release Repo** (`obs_plugin_github_repo`), the GitHub repo the
  Download button pulls the latest release from; **Minimum Plugin Version** (advisory only — older
  plugins still work but show an update banner); **Update Check Interval (h)**, how often the plugin
  checks for updates (default every 6 hours); and **Plugin Downloads Enabled**, a switch to disable
  the Download button entirely.
  - **Minimum Plugin Version** must be `X.Y.Z`, with an optional leading `v`, and is stored in that
    canonical form; leave it empty for no minimum. Anything else is refused under the row with
    "obs_plugin_min_version must be a version like 1.2.0 (X.Y.Z, optional leading v), or empty for
    no minimum".
  - The download comes from the latest GitHub release of the release repo, cached for 10 minutes.
    Reading the release needs the deployment's release-read token; without it, the plugin download
    is unavailable. Deployment details are in the kube-match-splitter repository's `DEPLOYMENT.md`,
    for people with repository access.
  - **Check now** — "Look up the latest plugin release now instead of waiting for the 10-minute
    cache." The button reads **Checking…** while it runs. The result shows "Latest: v*version*,
    published *date*" with a **Release notes** link, plus " — no Windows installer in this
    release" if the release has no installer; "No release found"; and "Last successful check:
    *time*". Checks are limited to 10 per 10 minutes across all admins; beyond that you get "Too
    many requests -- try again shortly". If no repo is set you get "No plugin release repository
    is configured (obs_plugin_github_repo)"; if GitHub refuses the token, the error says GitHub
    rejected the configured token.
- **Pairing** — **OBS Plugin Enabled**, a platform-wide kill switch for the pairing API (**off by
  default**); **Pairing Code TTL (min)** (default 15 minutes); **Device Token Lifetime (days)**
  (default 365 days); and **Token Rotation Grace Period (h)** (default 24 hours) during which an old
  and new device token both still work while a plugin picks up its refreshed token. See
  [[Event-Streaming-Management/Client-Administration/5. OBS Plugin Devices|OBS Plugin Devices]] for
  the client-facing side of pairing.

Platform-wide notification toggles (admin notifications on by default, client notifications off by

# Test Mode

Settings that shape how test events (see
[[Event-Streaming-Management/System-Administration/4. System Admins and Test Mode#Test Events|System Admins and Test Mode]]) behave, plus the OBS Test Clock's own display options.
The tab has **Match Settings**, **Test Events** and **OBS Test Clock** sections and shows the **OBS
Test Clock URL**.

- **Match Settings** — **Match Length (seconds)** (default 90), **Dwell Time (seconds)** — the
  seconds between a test match's end and its score being posted (default 10) — **Cycle Time
  (minutes)**, the minutes between test match starts (default 8.0), and **First Match Delay
  (seconds)**, the delay after the stream starts recording before match 1 (default 60). A line
  under the fields checks that match length + dwell time fits within the cycle time. See
  [[Event-Streaming-Management/System-Administration/4. System Admins and Test Mode#How Test Matches Are Scheduled|How Test Matches Are Scheduled]].
- **Test Events** — creating and listing test events.
- **Test Mode Uploads** (`test_mode_upload_enabled`, default **off**) and **Test Mode
  Re-Streaming** (`test_mode_restream_enabled`, default **off**) are **not on this tab**; they're
  set in the database only. Test uploads need the first on *and* an Operation Mode other than
  **Record Only**. The second applies to **manual-key** test events only, and only while
  **Manual-Key Re-Streaming** is on; a YouTube-channel-mode test event restreams whenever
  restreaming is enabled.
- **OBS Test Clock** — **12-Hour Clock** (default off, so 24-hour), **Timezone** (default UTC),
  **Show Color Bars** and **Show Diagnostics Row** (both on by default), **Beep Interval (s)**
  (default 10; 0 turns beeps off), **Top-of-Minute Chime** (on by default), **440Hz Reference
  Tone** (off by default), **Audio Channel** (both/left/right, default both) and **Volume (%)**
  (default 20). See
  [[Event-Streaming-Management/System-Administration/4. System Admins and Test Mode#OBS Test Clock|OBS Test Clock]].

# Settings That Change What Operators See

Some settings show up for operators as a disabled control with a reason, or as a countdown. When a
Client asks why something is greyed out, check these first:

| Setting | What operators see |
|---|---|
| Restream Integration Enabled (off) | **Start Push** and **Go Live** disabled with "🔒 Turned off by system administrators" |
| Keyframe Interval Check (off) | The keyframe warning's **Re-check** disabled with "🔒 Turned off by system administrators" |
| Stream Preview (off) | "🔒 Live preview turned off by system administrators" instead of the preview |
| Restream Hold Timeout (s) | The "gives up in *m:ss*" countdown while a push is holding |
