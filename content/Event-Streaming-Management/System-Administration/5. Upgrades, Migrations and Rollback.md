# Database Migrations

Schema changes ship as numbered migration files with a documented baseline-plus-ledger convention.
They're applied automatically as part of a normal deploy, or can be applied manually with the
platform's migration-apply script if needed.

# Redeploying a Service

A single service can be redeployed on its own (a rolling restart picking up a new image), without
redeploying the whole platform. A full release — triggered by tagging a new version — rebuilds and
redeploys only the services that actually changed since the previous tag, based on which paths in
the repository that tag touched.

# Rollback

The supported rollback path is to **re-tag a previous release** and let the normal deploy pipeline
ship it — this is simpler and more reliable than trying to "undo" a bad deploy in place.

> [!important] Automatic Rollback Is Best-Effort Only
> The deploy pipeline includes a best-effort automatic rollback step, but it is not the primary
> rollback mechanism and isn't guaranteed to fully restore previous state. It's held to one
> standard: if it or the deploy fails, it fails loudly (a clearly-failed job naming the affected
> service), never silently. Don't rely on it in place of the re-tag procedure above.
