# Database Migrations

Schema changes ship as numbered files (`db/migrations/NNN_short_description.sql`) applied in order
by a single migration runner, `db/apply-migrations.sh`. It tracks what's already applied in a ledger
table so re-running it is safe — only files not yet recorded get applied, each in its own
transaction. It's used automatically as part of every release (see below), but you can also run it
by hand against the cluster:

```
PSQL_CMD="kubectl exec -i -n <namespace> <postgres-pod> -- psql -U <db-user> -d <db-name>" db/apply-migrations.sh
```

Useful flags:

- `--dry-run` — list what's pending without applying anything.
- `--fail-if-pending` — exit with an error if anything is still pending (useful for confirming a
  deploy actually finished migrating before you move on).

Migration files are never edited after they've shipped, and numbers are never reused — if you're
adding your own migration, give it the next unused number.

# Cutting a Release

A release is triggered by pushing a version tag in the form `vX.Y.Z` (for example, `v1.4.0`):

```
git tag v1.4.0
git push origin v1.4.0
```

This is the trigger — merely pushing to `main` does **not** deploy anything by itself. Pushing the
tag kicks off the build/deploy pipeline, which:

1. Figures out which services actually changed since the previous release tag (based on which paths
   in the repository changed) and rebuilds/pushes only those images — the first release, or one that
   touches shared infrastructure paths, rebuilds everything instead.
2. Runs `db/apply-migrations.sh` against the cluster, every release, unconditionally.
3. Patches each changed service's Deployment to the new image and waits for the rollout to finish.

Releases are serialized — a new release won't start deploying while a previous one is still in
flight, so two deploys never race each other.

# Redeploying or Restarting a Single Service

To restart a single service without cutting a whole release (for example, to pick up a config
change or clear a wedged process):

```
kubectl rollout restart deployment/<service> -n <namespace>
kubectl rollout status deployment/<service> -n <namespace>
```

The admin Status page's **Restart** button (see
[[Event-Streaming-Management/System-Administration/6. Monitoring and Troubleshooting#Status Page|Monitoring and Troubleshooting]]) does exactly this under the hood, for any of the twelve
deployments listed in
[[Event-Streaming-Management/System-Administration/1. Architecture Overview#Services|Architecture Overview]] — it's the same action, just without needing cluster access.

# Rollback

The supported rollback path is to **cut a new release at an older, known-good commit** — tag it and
push, and let the normal deploy pipeline ship it forward, the same way any other release ships:

```
git tag v1.4.1 <known-good-commit>
git push origin v1.4.1
```

This is deliberately simpler and more reliable than trying to "undo" a bad deploy in place, and it
keeps the release history linear and auditable.

> [!important] Automatic Rollback Is Best-Effort Only
> The deploy pipeline also includes an automatic rollback step that fires if a release's deploy
> fails or is cancelled — it tries `kubectl rollout undo` on each service that was being updated,
> back to its pre-deploy revision. This exists to reduce blast radius from a broken deploy, but it
> is not the primary rollback mechanism and isn't guaranteed to fully restore previous state (it
> doesn't undo a migration, for instance). It's held to one standard: if it or the deploy fails, it
> fails loudly — a clearly-failed job naming the affected service — never silently. Don't rely on it
> in place of the re-tag procedure above; treat it as a safety net, not a plan.
