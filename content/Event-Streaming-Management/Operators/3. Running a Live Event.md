Open a configured event from its row on the Events page to reach its control center — the page
you'll use to monitor and operate it during the event itself. The header has an **Edit** link to
the event's full configuration page (it reads **View settings** if you can't change the
configuration). Everything below applies whether you're using the OBS plugin's dock or the web
dashboard; the plugin dock is a live mirror of this same page (see
[[Event-Streaming-Management/Operators/4. OBS Plugin Guide|OBS Plugin Guide]]), with a few
differences:

- The dock hides **Go Live** when there's no usable broadcast for today, instead of showing it
  dimmed, and its Go Live reason always reads "Start Push and wait for it to go active first".
- The dock hides **Enable Signage** outside the setup day and event days.
- **Stop Push** asks for confirmation in the dock just as it does on the web page.

Start/Stop Push, Go Live/Stop Broadcast and signage need **User** or above; Clear Stale needs
**Client Admin**. **Readonly** members see the same buttons dimmed with "🔒 Needs User or above",
and can watch the preview. Hover over a dimmed button to see why it's unavailable (or tap it, and
the reason shows as a message); primary buttons also show the reason on a line under the button.

# The Event Status Panel

Three status rows, each with a colored dot:

- **Incoming Stream** — gray "Offline" until the platform is actively receiving your OBS/RTMP
  stream; then "Online" plus resolution, bitrate, and codec.
- **YT Restream** — the push to YouTube; see [[#Starting and Stopping the Push|below]] for the
  full set of states. With no restream target it reads **Not configured** with a **Set a target**
  link. One line under the row gives more detail:
  - "Today's broadcast: *status*" (YouTube's own lifecycle status for today's broadcast, e.g.
    ready, live or complete);
  - "No broadcast for today yet. Create one" (the link opens the event's Livestream settings);
  - "Manual RTMP key mode" when the event pushes to a restream key instead of a
    platform-managed broadcast.
- **Signage** — "Unavailable" (no stream key), "Not controlling", "Controlling signage", or
  "Controlled by "*another event*"" if a sign this event would use is currently driven by a
  different event.

# Starting and Stopping the Push

The **Start Push** / **Stop Push** buttons appear when the event has a restream target set (a
YouTube channel or a manual RTMP key). Sending your incoming stream onward is a separate step from
publishing it to viewers.

In YouTube-channel mode the push sends video from the event's current stream key to **today's
broadcast** (today in the event's timezone), and it stays on that broadcast until you stop it,
even past midnight. If there's no broadcast for today, Start Push is refused; it never falls back
to another broadcast. See
[[Event-Streaming-Management/Operators/8. YouTube Broadcasts|YouTube Broadcasts]] for creating
broadcasts.

**Start Push** has no confirmation prompt. When the push can't start, the button is dimmed with
its reason under it; if the push is refused when you click, a "Failed to start push" dialog shows
the reason. The reasons are:

- "Configure this event first"
- "Set a restream target in the Livestream config section first"
- "Push is already running"
- "Wait for the push to stop"
- "Pushing opens at the event's start time. Video coming in now is a pre-event test feed."
- "No stream is coming in: the stream is not live on this event's stream key. Start streaming,
  then start the push."
- "No YouTube broadcast for today (*date*, *timezone*) -- create one on the event page"
- "The YouTube broadcast for *date* has ended (status: *status*) and can't receive video again --
  replace it with a new broadcast on the event page to push again"
- "🔒 Turned off by system administrators"

**Stop Push** always asks first, both here and in the OBS dock. The dialog is titled **Stop
Push?** with a **Stop Push** button, and its message depends on what the push is doing:

- While holding: "The push is holding on a standby slate and will resume by itself when OBS
  reconnects. Stop anyway?"
- While today's broadcast is live: "Today's broadcast is live on YouTube -- viewers will see the
  stream end."
- Otherwise: "Stop sending the stream to YouTube?"

Stop Push is never dimmed for a state reason; you can always stop a push.

The **YT Restream** row shows one of these states:

| State | Colour | Meaning |
|---|---|---|
| **Not configured** | gray | No restream target is set |
| **Idle** | gray | Not pushing; the line under it gives the last stop reason, e.g. "Stopped by operator" |
| **Starting push…** | blue | The push is starting |
| **Holding — standby slate on YouTube** | amber | OBS disconnected; see below. The line under it reads "Resumes automatically when OBS reconnects · gives up in *m:ss*" |
| **Pushing** | green | Manual RTMP key mode only: the push is running |
| **Pushing — waiting for YouTube** | amber | Pushing, but YouTube isn't receiving it yet |
| **Pushing — ingest *health*** | amber | YouTube receives the push but reports a problem with it |
| **Ready for Live** | green | YouTube is receiving the push (YouTube-channel mode); you can **Go Live** |
| **Live to YouTube** | green | Today's broadcast is live |
| **Stopping push…** | amber | The push is stopping |
| **Push error** | red | The line under it gives the error detail; **Readonly** members see "The push failed" |

**Holding.** When OBS drops after the push has started, the push keeps YouTube's broadcast open
with a generated standby slate — a plain black picture with silence and no text — so YouTube
doesn't end the broadcast for lack of data. Viewers see the black slate. The push resumes by
itself when OBS reconnects, so reconnect OBS rather than pressing Stop Push. If OBS doesn't come
back within the system's **Restream Hold Timeout** (10 minutes by default), the push gives up with
an error ending "Source did not return within *N*s -- giving up". A push whose source never
started publishing gives up the same way, with "Source never started publishing within the
configured hold timeout -- giving up".

> [!warning]
> **Ready for Live** and **Live to YouTube** mean YouTube is *receiving* the push, not that
> viewers can play it. The dashboard has no "YouTube is playing" indicator. See
> [[Event-Streaming-Management/Operators/6. Troubleshooting#YouTube Shows Healthy but Won't Play|YouTube Shows Healthy but Won't Play]].

# Going Live and Stopping the Broadcast

In YouTube-channel mode two more buttons act on today's broadcast:

- **Go Live** — publishes today's broadcast to viewers. No confirmation prompt. It always shows;
  when it can't be used it's dimmed with the reason under it. It needs the push to be active
  **and** YouTube to be receiving it (YouTube's health rating doesn't have to be "good"). The
  reasons are:
  - "Start Push and wait for it to go active"
  - "Wait for the push to go active"
  - "Today is not a broadcast day — add it under Broadcast days on the Livestream tab"
  - "Create today's broadcast on the Livestream tab first"
  - "This YouTube broadcast has ended — replace it to go live again"
  - "🔒 Turned off by system administrators"

  If YouTube itself refuses, you'll see: "The stream isn't receiving data from the push yet
  (YouTube reports '*status*', needs 'active'). Make sure Start Push is running and healthy, then
  try Go Live again."
- **Stop Broadcast** — takes Go Live's place while today's broadcast is live. It confirms first
  with a **Stop this broadcast?** dialog: *"Stop this broadcast? This is irreversible on YouTube —
  the broadcast cannot be resumed."* Use this deliberately — there's no way to resume the same
  broadcast afterward.

In short: start streaming in OBS and confirm the **Incoming Stream** row reads **Online**, then
**Start Push** and wait for the **YT Restream** row to read **Ready for Live**, then **Go Live**;
the row reads **Live to YouTube** once live. To end the stream, reverse it — **Stop Broadcast**
first, then **Stop Push** (which asks for confirmation), then stop streaming in OBS.

## Replacing Today's Broadcast

A broadcast that has ended on YouTube can't go live or receive video again. You can replace it
from the Broadcast days section of the event's Livestream settings. Replacing asks for
confirmation first and creates a **new YouTube video with a new public link** — viewers with the
link you already announced won't see it. It's refused while the broadcast is live. See
[[Event-Streaming-Management/Operators/8. YouTube Broadcasts#Replacing a Broadcast|Replacing a Broadcast]]
before you do it.

# Signage Controls

If the event has a stream key, **Enable Signage** / **Disable Signage** buttons appear. Both need
**User** or above. Turning signage on is allowed from the event's **setup day** (the day before
the event starts) through its last day, in the event's timezone; turning it off is allowed on any
day. System admins aren't limited by the dates. The refusals you may see are:

- "Signage can be turned on only on the setup day and event days (*setup day* to *last day*)"
- "Signs are controlled by "*other event*" — turn signage off there first"
- "Assign a stream key to this event first"

Disabling confirms first with a **Disable signage control?** dialog: *"Disable signage control for
this event? Signs on its stream key will return to the idle page."* and a **Disable** button. See
[[Event-Streaming-Management/Operators/5. Clips, Uploads and Signage#Signage|Clips, Uploads and Signage]]
for assigning signs and switching what they display.

# Live Preview and Pipeline Progress

The control center includes a live preview. Any member can watch it unless system administrators
have turned previews off. The **System Feed** tab plays the incoming stream (it works during a
pre-event test too); the **YouTube** tab embeds today's YouTube broadcast.

When the preview isn't available, the reason shows in the video box: "🔒 Live preview turned off
by system administrators" or "The stream isn't live — there's no incoming feed to preview". If the
player itself fails you may see:

- "Preview access was refused — the preview link may have expired. Reopen the preview to try
  again."
- "Stream unavailable — ensure the event is live and actively streaming."

Below the preview, a pipeline section shows each match's progress through recording, clipping,
and uploading. Clip creation and YouTube publishing happen automatically as matches are detected —
there's no manual "publish" step during the event. A clip held for review sits in its own **Needs
Review** stage alongside pending/processing/failed, so it isn't mistaken for a pipeline error; see
[[Event-Streaming-Management/Operators/5. Clips, Uploads and Signage|Clips, Uploads and Signage]]
for what to check afterward and how to approve or discard it.

# Health Warnings

Warning banners appear on the status panel when something needs attention — for example, an
incompatible video or audio codec, a keyframe interval that's too long for reliable clipping, or
an issue YouTube itself reports about the incoming stream. See
[[Event-Streaming-Management/Operators/6. Troubleshooting#Health Warning Banners|Troubleshooting]]
for the exact wording and thresholds behind each one.

There is no check for missing audio. A stream can pass every check, and YouTube can call it
healthy, yet not play. See
[[Event-Streaming-Management/Operators/6. Troubleshooting#YouTube Shows Healthy but Won't Play|YouTube Shows Healthy but Won't Play]].

# If a Session Gets Stuck

A live event whose incoming stream has stopped heals itself within about 2 minutes, so this is
rarely needed. If the dashboard still thinks your event is live after your stream has actually
stopped, a **Client Admin** can use **Clear Stale**, which appears on 🔴 LIVE rows of the Events
list. It confirms with a dialog titled *"Force-close the stale live session for "*event name*"?"*,
the message *"The event is closed even if it is still marked live."* and a **Force-close** button.

This only cleans up the platform's own bookkeeping — it does **not** stop an actual OBS/RTMP push
or an active YouTube broadcast, and it doesn't delete anything already recorded or clipped. If
your stream or broadcast is genuinely still running, stop it from OBS (and, if applicable, **Stop
Broadcast** / **Stop Push** above) first.

The same Events list has **Complete** (needs **User**; marks an in-progress or live event as
completed) and **Reopen** (needs **Client Admin**; returns a completed event to In Progress).
